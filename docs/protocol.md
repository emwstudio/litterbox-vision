# 本地协议与计数规则

## 信任边界

- ModelBest 密钥仅存在于电脑 `MODELBEST_API_KEY`。
- ESP32 使用 `X-Device-Token` 访问设备接口。
- 电脑本机回环地址可访问控制台；猫档案修改还要求 `X-CatVision-Action: local`，阻止普通跨站表单直接提交。
- 媒体路由只允许读取 `DATA_DIR` 内已存在文件，规范化路径后阻止目录穿越。
- 首版是局域网 HTTP，不含公网 HTTPS、账号系统或远程访问隧道。

## 摄像头接口

| 接口 | 含义 |
| --- | --- |
| `GET /stream` | 800×600、传感器直出 JPEG 的 MJPEG |
| `GET /snapshot` | 单张 JPEG |
| `GET /health` | 在线、宽高、实测采集帧率、帧龄、采集/发送错误与会话计数 |

摄像头采集任务与 HTTP 发送分离，发送端只复制最新帧，并将 MJPEG 包头与 JPEG 合并为一次发送。`fps` 是实测采集帧率，不再用配置值冒充实测值。

## 电脑设备接口

| 接口 | 含义 |
| --- | --- |
| `GET /api/layout` | 画面尺寸、旋转和四个盆的归一化区域 |
| `PUT /api/layout` | 校验并保存区域，同时生成四张实景徽章 |
| `GET /api/frame.jpg` | 当前原始 JPEG |
| `GET /api/display/frame.jpg?target=monitor|stats|stats_top&overlay=true|false&format=jpeg|rgb565|zlib` | `monitor` 为 466×466、`stats` 为 480×480 的等比完整预览；`stats_top` 为 480×240 的居中填满 LIVE；RGB565 为小端原始像素，`zlib` 对同尺寸 RGB565 字节做无损压缩 |
| `GET /api/display/stats.json?date=YYYY-MM-DD` | 四猫日报、头像、偏好徽章、未知身份和盆总数 |
| `GET /api/media/{path}` | `DATA_DIR` 内的头像、徽章、封面或录像 |

两块屏的 LIVE 使用电脑端口 8001 的原始 TCP 会话。设备发送 `CVLT` 握手及设备令牌，中枢返回 `CVOK`。每个 `CVP1` 帧头为 `<4sIIHH`：魔数、正文长度、整帧 CRC、增量标记和分区数（当前为 8）。正文有八个 `<IIIB3x` 记录：压缩长度、该分区还原后的 CRC、原始长度和增量标记；各分区分别使用 zlib 压缩。像素为适配 LCD 的大端 RGB565，解压还原后仍为 434312 字节（`monitor`）或 230400 字节（`stats_top`）。

设备收满一帧后发送 `CVAK + 整帧CRC` 作为**接收确认**，让中枢准备最新帧；这个确认不代表已经显示。设备随后并行完成八个分区的解压、XOR 和分区 CRC，再合并校验整帧 CRC，通过后才交给标准 LVGL 更新图像。任何解压、长度或 CRC 错误都会关闭会话并重连，下一连接首帧强制为完整帧，不沿用可疑增量。

接收使用两个 PSRAM 缓冲，两个工作核动态领取分区。当前 LIVE 使用标准 LVGL 与 BSP 显示，不绕过 LVGL 直写 LCD。`catvision_lvgl_present_owned_be` 分别保留原始大端增量基准和 LVGL 原生字节序显示缓冲；同尺寸原生缓冲复用，复写前等待 LVGL 完成旧画面的读取，尺寸变化时才重新分配。LCD 中断回调只记录完成计数和时间戳，日志在普通任务上下文打印。zlib 解压热点通过 `catvision_display/linker.lf` 放入 IRAM，第三方源码不改。双核解压任务使用 PSRAM 栈；2.16 统计屏的 LIVE 任务也使用 16KB PSRAM 栈，其统计任务保留内部 RAM。

HTTP 的旧 `frame.jpg` / `zlib` / `zlib_delta` 接口保留，不能把原始 TCP 的大端分区格式误用于这些接口。16fps 是性能目标而不是已完成承诺；必须以屏幕实际新帧间隔和完整错误日志验收，不能用重复帧或中枢编码速度代替。

`Rect` 使用 `x/y/width/height`，全部归一化到 0..1。所有盆有 `bounds`；带盖盆另有 `entry` 与 `exit_top`。旋转后的画面、模型图、显示图与徽章使用同一坐标约定。

## 管理接口

- `GET /api/cats`
- `POST /api/cats`：`multipart/form-data`，字段 `name`、`avatar`、`references`；参考图 5–10 张，每张不超过 10MiB。
- `POST /api/cats/{id}/references`：追加参考图，总数不超过 10 张。
- `GET /api/stats/daily?date=YYYY-MM-DD`
- `GET /api/events?date=YYYY-MM-DD`

头像在保存时居中裁剪为 64×64 JPEG；徽章也是 64×64，避免依赖嵌入式 JPEG 解码器缩放。

## 模型分工

1. ROI 帧差检测运动，避免对每一帧调用云端模型。
2. 经同帧实测与用户确认，MiniCPM-V-4.7-35B-A3B 对整帧只做一次初筛，返回 `observations` 与 `empty_box_ids` 两个数组。每个实际物理猫使用帧内唯一的 `subject_id`，并提供整帧归一化 `cat_center=[x,y]`、盆 ID 和动作；同一物理猫不得跨盆重复，不同猫必须分开。`observations` 只包含实际看到的猫，确认无猫的盆写入 `empty_box_ids`，不为凑数编造猫。缺盆或 `box_id=null` 只表示无有效观察，不关闭活动事件。顶层数组也兼容；单个无效项跳过，不影响其他有效项。
3. 写入事件前先做位置校验与仲裁：有猫动作除 `leave` 外，中心须位于对应盆/动作区域的 0.02 容差内；同一 `subject_id` 且中心距离小于 0.08 时只保留位置有效、置信度更高、距盆中心更近的一项，相同标签但明显不同位置不合并。每盆最多一项观察，不再强制覆盖模型盆 ID。
4. MiniCPM-V-4.7-35B-A3B 也在有效访问离场或连续无猫结束时，使用本次事件保存的有猫关键帧复核身份与前后一致性，不改写初筛判断的进入、停留、离开动作。
5. 图像通过 OpenAI 风格的 `image_url` 内容块发送，默认使用 base64 data URI。若平台拒绝，必须在适配层改用官方文件上传方式；局域网 URL 对云端无意义。
6. 返回内容必须是符合结构的 JSON；无效输出可重试一次，仍失败则记录调用错误。活动事件遇到短暂初筛异常时继续保留并重试，不立即关闭；身份复核失败时使用 `unknown` 保留使用次数。无猫返回允许 `box_id=null`，按无事件处理；缺少 `confidence` 时按 `0.0` 处理。数字盆 ID `1–4` 归一化为 `box-1` 至 `box-4`，数字 `0`、空值或无有效盆时跳过该次观察，不误关闭活动事件。`429` 响应按 `Retry-After` 等待，未提供时至少等待 2 秒，单次等待上限 30 秒。

动作枚举：`enter`、`inside_toilet`、`exit_top`、`leave`、`none`。

## 计数状态机

### 带盖盆

`enter` 建立活动事件，至少 8 秒后出现 `exit_top`，或连续 10 秒无猫，才生成一次 `counted / inferred=true`。孤立顶部出口、过短访问、超过 30 分钟无出口均不计数。空盆结束也会做一次身份复核，失败时保留 `unknown`。

### 开放盆

首次 `inside_toilet` 建立活动事件，静止在盆内也算，不要求蹲姿或排泄证据。至少两次盆内观察的首尾时间横跨 8 秒，随后收到 `leave`，或当前盆连续 10 秒无猫，才结束并计为 `counted`；单次无猫不会立即结束，新的有猫结果会重置无猫等待。孤立 `enter` 不建立事件。只有一次盆内判断、证据跨度不足 8 秒、只进入或路过时记为 `discarded`，避免单帧误报形成计数。身份复核使用本次事件保存的有猫关键帧，不再从整个长时间段均匀抽取空画面；`event_toilet_observed` 仅作为协议兼容字段保留。这里的统计表示猫砂盆使用次数，不严格等于实际排泄次数。

### 共用规则

- 每个盆同一时刻最多一个活动事件，完成前重复动作不重复加数；活动期间每 5 秒低频采样，静止猫不完全依赖帧差运动。
- 活动事件在电脑重启时关闭为 `error`，超过 30 分钟由独立超时推进关闭，不依赖下一次运动。
- 低置信但结构完整的事件仍直接计数并保存置信度，不要求人工复核。
- 身份证据不足使用 `unknown`：进入盆总数，不硬猜某只猫。
- 短暂初筛异常保留活动事件并继续重试；身份复核异常使用 `unknown` 保留计数；录像写入失败记为 `error`，不进入日报。
- 日报以事件 `started_at` 所属的 `Asia/Shanghai` 自然日为准。
- 当天最高使用次数并列时返回多个徽章；没有事件时偏好为空。
- 录像默认包含事前 15 秒、事件过程和事后 15 秒，使用 H.264 MP4，并带 16kHz 单声道 AAC 音轨。事件确认后即建立独立帧文件；创建时的缓存从事前 15 秒延伸至创建时刻，包含等待模型返回期间到达的帧和音频，不再只截取到模型观察时刻。后续视频帧通过回调逐帧追加，不经过低频识别循环，长事件不受全局 45 秒缓存淘汰影响。编码按采集时间戳重采样并补复用帧，掉帧或帧率变化不会直接改变事件时长。UDP 音频缺包按序号补静音并计数。`counted`、`discarded` 和 `error` 的已结束访问都生成复核视频，状态不影响日报统计口径。中枢关闭时保留活动事件的原始帧和音频文件，不再直接删除，便于后续恢复；重启时活动事件仍按 `error` 关闭。

## 已知边界

单摄像头严重遮挡、多只猫同时进入同一盆、系统启动时猫已经在带盖盆内、相似花色和异常停留都可能造成漏计或误计。当前方案是一般视觉模型加行为状态机，不等同于经过专用猫身份模型验证的医疗级监测。

## 2026-11-16 UDP 丢帧治理与实测

- 事件初始化计时对照：`EventRecorder.start` 约 0.0046 秒，排除了事前 15 秒缓存写入造成卡顿。对照录像期间出现 82 个不完整 UDP 帧，确认问题在视频传输链路。
- 接收端重组允许乱序：最多暂存 4 个未完成帧，500ms 抖动超时；不再因新序号提前到来就丢弃旧帧，已完成帧只去重。
- 摄像头固件 `1.0.2` 在每 4 个 UDP 分包后让出 1ms，降低瞬间发送冲击，不降低分辨率或目标帧率。
- 部署后 30 秒实测：完整接收 484 帧，不完整帧 0、重复帧 0、CRC 错误 0、音频缺样 0；摄像头采集约 16.1 FPS，UDP 未进入备用模式。此结果只代表本次实测，后续仍需用真实猫事件复核关键时刻视频。
- 固件 `1.0.3` 起，`/health` 增加 `udp_sent_frames`、`udp_packets_sent`、`udp_send_errors`、`udp_sequence`、`udp_capture_sequence`、`udp_frame_bytes`、`udp_last_socket_error`。`udp_sent_frames` 表示进入发送流程的帧数，不能单独证明所有分包已经到达。
- 中枢 `/api/health` 的 `udp_ingest` 增加有效分包计数 `packets`、整帧序号缺口 `sequence_gaps`、来源地址 `sources`、当前暂存 `pending` 和最近 32 次不完整帧 `recent_losses`。每条丢帧记录包含序号、首末分包时间、收到/总分包数、缺失下标，以及 `timeout` 或 `pending_limit` 原因。
- 已实测到 `sendto()` 返回 `ENOMEM(12)`；lwIP 在 UDP `netbuf` 分配失败时返回该错误。每包让出 1ms 后仍复现，因此固件 `1.0.5` 不再依赖加大延时，而是只对 `ENOMEM` 做最多 4 次、每次间隔 1ms 的有限重试。`udp_retry_successes` 记录恢复成功，`udp_send_aborts` 记录最终放弃，`udp_last_error_sequence/index` 定位出错分包；曾经报错但重试成功不等同于缺帧。

## 可靠 UDP 补包（固件 1.1.0）

- `CVJ1` 视频包格式不变。新增 28 字节 `CVN1` 补包请求，小端结构 `<4sIHH16s`：帧序号、首分包下标、分包数量、128 位缺失位图。数量为零表示整帧补发，此时首下标和位图也必须为零；部分请求的位图相对于首下标，不能超出请求范围。
- 中枢从 UDP `5060` 向摄像头 `5062` 请求。摄像头只接受当前中枢 IP、来源端口 `5060` 的合法请求；补发仍是普通 `CVJ1`，使用同一 CRC 和 JPEG 解码路径。
- 摄像头按实际 JPEG 大小在 PSRAM 保存最近 64 帧、最多 4MiB；发送中途失败的完整 JPEG 也入缓存。读写和淘汰持锁，锁外发送。健康字段 `udp_history_frames`、`udp_history_bytes`、`history_drops`、`nack_requests`、`retransmitted_packets` 用于对照缓存与补发。
- 中枢最多暂存 64 帧且最多 4MiB，未知长度的整帧缺口不分配 JPEG 缓冲，序号突跳最多登记 128 帧。部分帧在 40/200/600/1400ms 请求，2500ms 后才算最终不完整；每 20ms 最多为两个帧发请求。健康字段 `nack_requests`、`repaired_frames`、`repair_timeouts`、`last_repair_ms` 区分请求、补回与超时。
- 完整帧收齐立即显示，不等待更早的帧。重复补包只去重；部分帧按首次分包时间、整帧缺失按相邻时间插值写入有序 `FrameRingBuffer`，不能用补包完成时间冒充拍摄时间。模型与运动检测仍处理最新帧，录像合成继续按时间戳排序。
- `udp_send_aborts` 只表示当次发送最终放弃，不等于该帧最终丢失；后续 `CVN1` 可能补回。历史已淘汰、持续断网或超过 2500ms 仍不完整时必须保留失败记录，不能宣称可靠 UDP 在断网时零丢帧。
